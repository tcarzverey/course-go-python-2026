# Почему печатается `a=` (переупорядочивание записей на arm64)

## Расстановка

`main` и `setup` крутятся на **разных ядрах CPU** (потому и параллелизм). У каждого ядра — своя L1-кэш и свой **store buffer** (буфер записи). Когда ядро выполняет запись, значение **не летит сразу в общую память**, а сначала падает в этот буфер и оттуда асинхронно «расходится» по системе кэш-когерентности к другим ядрам.

Критично: `a` и `done` — это **разные переменные в разных строках кэша**. Каждая строка распространяется к другому ядру **независимо и с разной задержкой**. Без барьера памяти железо ничего не обещает про порядок, в котором эти две записи станут *видны* соседнему ядру.

## Что произошло по времени

Ядро A выполняет `setup`, ядро B крутит `for !done {}`:

```
Ядро A (setup)                     Ядро B (main, спинит в цикле)
------------------------------     ----------------------------------
a.len = 5    ┐                      load done → false, крутимся
a.ptr = &"H" ┤ лежат в store buffer load done → false, крутимся
done = true  ┘ ещё НЕ видны B       load done → false, крутимся
                 │
   [запись done долетает до B]
                 │                  load done → TRUE! выходим из цикла
                 │                  load a → запись a ЕЩЁ не долетела
                 │                          → читаем старое ""   ← ВОТ ОНО
   [запись a долетает до B, но уже поздно]
                                    a != "Hello" → печатаем a=[], break
```

Всё. `done` «выиграл гонку» за видимость: его строка кэша дошла до ядра B на несколько тактов раньше, чем строка с `a`. Ядро B успело прочитать `done == true` в этот крошечный промежуток, когда новое `a` ещё в пути.

Важный нюанс: инструкции на ядре A выполнились **по порядку** — это не «процессор переставил команды местами» в том смысле, что в дебаггере ты бы это увидел. Переставился **момент, когда каждая запись стала видна другому ядру**. Это и есть «переупорядочивание store→store» в терминах модели памяти.

## Почему «узкое окно» и десятки тысяч итераций

Разрыв между «`done` виден B» и «`a` виден B» — это буквально задержка распространения одной строки кэша: единицы–десятки наносекунд, несколько тактов. Чтобы баг проявился, ядро B должно прочитать `done` **ровно** в этот зазор.

Почти всегда к моменту, когда B проверяет `done`, **обе** записи уже давно долетели (setup ведь пишет их подряд), и B видит `a == "Hello"`. И только изредка тайминг случайно попадает точно в щель — отсюда и «сломалось на 18196-й итерации», а не на каждой. Это и есть маркер настоящей микроархитектурной гонки: редкая, тайминг-зависимая, в отличие от сломанной логики ожидания, где `a=` вылезал бы детерминированно.

## Почему на x86 этого не было

У x86 модель памяти **TSO**: store buffer есть, но железу запрещено давать другим ядрам увидеть две записи в порядке, обратном программному (store-store не переставляются). Поэтому если B увидел `done == true`, то `a = "Hello"` там **гарантированно уже видно**. Окна не существует → под Rosetta не сломалось ни разу.

Барьер памяти (или атомик/канал/мьютекс в Go) как раз заставляет ядро A «продавить» store buffer и опубликовать `a` до публикации `done` — тогда окно закрывается и на arm64.
